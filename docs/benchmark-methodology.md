# Benchmark methodology

Exploratory live NVIDIA runs are recorded in the [development evidence log](live-evaluation-2026-10-22.md). A separate, limited [live held-out protocol](live-held-out-2026-10-22.md) has also finished; it sampled one fixed variant per fault family and one trial per configuration. Neither supports a general reliability rate. Fixtures and mocked-provider results validate software behavior only.

The fixed packs in `skylark.wind.benchmark` separate development and held-out cases. The held-out pack has four parameter variants for each fault family. Resource, customer, capacity, intent, and seed vary; faults attach to explicit eligible calls. This is a narrow synthetic set, not a representative production sample.

Freeze the pack hash, model/settings, prompt, policy, and verifier before evaluation. Target 12 fault scenarios × 3 fresh trials × 2 configurations plus six controls. Each attempt starts from a fresh snapshot. Compare identical tasks and faults.

An untriggered fault is inconclusive, not passed. Include infrastructure errors, incomplete attempts, denominators, and uncertainty. Repetitions on the same scenario are correlated. Report safety, completion, factual final reporting, coverage, tool calls, latency, and cost separately. Distinguish runtime safeguards from prompt changes and disclose required tool contracts.

The current `reservation/5` verifier checks the structured booking outcome and recognized explicit numeric post-booking availability claims, including subsequent checks, “slots still available,” and “availability remains at N” wording. It cannot establish truth of arbitrary free-text explanations. Report that limit alongside the reporting-accuracy count. Earlier `reservation/2`, `/3`, and `/4` verdicts retain their historical replay semantics; do not pool their recorded scores with `/5`. Live stale-read tasks request a post-booking read; the fixture script already performs one. The scheduled scenario snapshot and pack hash include that live task message.

The report command and Results screen implement these dimensions with passed/failed/unknown counts. Fault-free controls have no fault-coverage denominator. Rates use observed checks; pending, interrupted, and infrastructure-failed attempts remain visible as unknown. Descriptive 95% Wilson intervals assume independent trials, an assumption repeated scenarios do not satisfy; do not use them as guarantees. Median latency and tool-call counts include only attempts with recorded measurements, with observed counts retained. Costs include all provider calls attributed to the run, including diagnosis, and retain unconfirmed reservations.

Groups separate model/settings, policy, agent, tool, verifier, environment, execution limits, condition, and split. Use `skylark report --comparison ID --output results.json` to freeze a scoped report after the planned jobs complete. The scoped export includes every scheduled run, including failures; a global report also includes exploratory runs and must not be presented as a predeclared benchmark.

The benchmark refuses protocols exceeding the conservative configured allowance. Predeclare fewer trials before collecting results if needed. Never select only successful trials or discard expensive failures.

The CLI can also predeclare `--cases-per-fault 1` through `4` for the held-out split. This always takes the first N fixed variants in each fault family before any result is observed; the chosen count, scenario pack hash, full protocol hash, and complete scheduled run list are stored with the protocol. `--freshness-guard` adds read freshness validation only to the repaired configuration and is recorded separately. With one case per fault and one trial, the protocol has six fault runs plus six controls. Treat this as a limited held-out sample with one variant per family, not as the 78-run target; report each configuration and fault family separately. A later full protocol needs a separate ID and sufficient verified credit.

With the configured $0.50 allowance and $0.06/$0.24 per-million input/output rates, the conservative reservation for each completed 12-attempt live protocol was about $0.370944. Local estimates were $0.007013 for development and $0.008189 for the limited held-out protocol. The full 78-run held-out pack would reserve about $2.411136 and remains blocked by the cap. These reservations are upper bounds, not expected charges. Protocol `87c2e90bfde04ffd985b0417aed97838` is recorded in the [development log](live-evaluation-2026-10-22.md); protocol `99564c8636104684b1b7d0b871bef639` is recorded in the [limited held-out log](live-held-out-2026-10-22.md). Keep their results separate. Verify provider credits and adjust the allowance deliberately before scheduling a larger live protocol.

The post-development-pack `validate_freshness` policy option was included on the repaired side of the limited held-out protocol. Each run snapshot includes this policy field. The scenario pack hash covers scenarios and tasks; the full protocol hash also covers both configurations, limits, verifier version, and model settings. Do not reuse either archived protocol ID or treat a later candidate comparison as part of its predeclared result. Freeze a separate protocol before any future held-out evaluation.

The initial model probe has a $2 ceiling and at most two available NVIDIA candidates. Select the lowest-cost model that actually supports native tool calls and structured completion for this task. Record identifiers, rates, usage, malformed-output frequency, and latency. Catalogue availability does not establish working access.

Claim template: "On [N] predefined synthetic scenarios and [R] fresh trials per configuration, [model/settings] produced [counts]. The [prompt/runtime] change altered safety from [a/n] to [b/n], and completion from [c/n] to [d/n], with [e] uncovered and [f] infrastructure-failed attempts. This does not establish general agent safety."
